## 1. 范围与结论

2026-09-12 按「写操作成功后，优先使用返回结果更新前端，不为已知字段重新查询」调整代码，并静态检查了图库、收藏、回收站、相册、标签、管理页、分享、鉴权、上传、后台任务、数据库查询和静态资源。2026-09-13 在当前工作区基础上复审，重点补充共享相册、视频总结推送、上传完成链路和浏览器布局开销。

**按要求没有运行测试、类型检查、构建、压测或浏览器性能采样。** 本文的请求变化来自调用链分析，不是实测数据；剩余条目是代码中已发现的开销或性能风险，不代表已经证明生产环境存在慢查询，也不声称穷尽所有运行时瓶颈。

核心结论：收藏成功后再获取图库、详情、统计、相册和标签，确实属于不必要的开销。但首次加载、换页、权限校验、未知数据和异步任务结果不是同一类请求，不能一并删除。

优先级说明：

- **P1**：高频路径，随媒体数、用户数或请求数明显放大，建议优先优化。
- **P2**：特定页面、大批量操作或首屏资源开销，建议分项优化。
- **P3**：低频路径或需要部署数据才能确认，先记录和测量。

## 2. 已修复：写操作引发的无关刷新（历史实施记录）

### 2.1 根因

原来的调用关系：

```text
收藏 / 删除 / 修改集合等操作成功
  → workspace.perform()
  → workspace.invalidate()
  → 全局 revision 变化，同时重新获取 overview
  → useAssetFeed / useRemoteData 的订阅者重新请求
  → KeepAlive 中已离开的页面也可能请求
  → 列表清空重建，缩略图重新加载，分页位置丢失
```

现在的调用关系：

```text
操作成功
  → 读取接口返回值
  → 发布有类型的局部变更
  → 更新已加载列表、详情、集合摘要及已知统计字段
  → 只有无法由已有数据推导的资源，才按范围失效
```

主要实现：

- `apps/web/src/stores/workspace.ts`：操作成功回调、局部变更、已知资产缓存、统计增量和按资源失效。
- `apps/web/src/types/workspace.ts`：明确资产、相册、标签、关联及管理记录的变更类型。
- `apps/web/src/composables/workspaceUpdates.ts`、`adminUpdates.ts`：集中处理字段、关系和计数更新。
- `apps/web/src/composables/useAssetFeed.ts`、`useRemoteData.ts`：应用局部变化、保留分页，暂停失活页面的请求，并处理旧请求与新状态的竞争。

### 2.2 操作调整清单

| 操作                             | 现在的行为                                                                  | 不再附带的查询                                   |
| -------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------ |
| 收藏 / 取消收藏                  | 使用返回的 `{ id, isFavorite }`，同步列表、详情、收藏页及收藏计数           | 不重拉图库、详情、overview、相册或标签           |
| 移入回收站 / 恢复 / 永久删除     | 更新 `deleted` 等字段，移除或插入已知项目，按缓存中的资产大小和状态调整统计 | 不重拉当前列表及已知统计                         |
| 新建 / 修改 / 删除相册，设置封面 | 用返回摘要替换对应相册，更新已知关联和相册总数                              | 不重拉相册列表及图库                             |
| 添加 / 移出相册成员              | 用返回的 `album` 更新计数、封面和关联；可确定筛选条件时直接更新成员列表     | 不额外查询整份相册列表或相册详情                 |
| 新建 / 改名 / 删除 / 合并标签    | 更新标签、已加载资产标签和已知分组计数                                      | 不重拉所有分组和图库                             |
| 添加 / 移除资产标签              | 使用接口返回的标签摘要，逐项更新；批次中成功的项目立即生效                  | 不在每张图片修改后重拉列表；失败或取消不全局刷新 |
| 创建 / 撤销分享短链              | 直接插入新链接或设置对应链接的撤销状态                                      | 不重拉分享链接列表                               |
| 保存他人的分享                   | 记录保存结果，目标资源延迟到进入工作区时获取；重复保存不失效缓存            | 不在公开分享页请求用户图库和统计                 |
| 重试媒体处理                     | 使用返回的 `PENDING` 更新任务状态，清空旧失败字段                           | 不立即重拉任务列表和统计                         |
| 单张图片提交识别                 | 按入队结果更新为待处理，后续轮询只获取真正的异步结果                        | 不在入队后立即重复查识别详情                     |
| 用户 / 角色 / 权限管理           | 用保存结果替换记录并更新关联计数；用户翻页复用当前页面已有角色和权限目录    | 保存后不重拉整页；翻页不重拉角色和权限           |

收藏的静态调用链预期：在数据已加载、会话和 CSRF 令牌有效的情况下，一次点击只有一次收藏写请求，**由该操作额外触发的数据查询为 0**。首次 CSRF 签发、令牌续期、用户手动刷新和恰好到期的后台状态轮询不属于这个计数。

### 2.3 配套接口返回值

为避免把 HTTP 请求移除后改成前端猜测计数、封面，服务端在原有事务内返回对应摘要：

| 接口                                                   | 返回值                                                                  |
| ------------------------------------------------------ | ----------------------------------------------------------------------- |
| `POST /albums/:id/assets`、`DELETE /albums/:id/assets` | `{ count, album }`，`album` 为修改后的相册摘要                          |
| `POST /assets/:id/tags`                                | `{ tags, createdCount }`，`tags` 为资产当前全部标签摘要，包含计数和封面 |
| `DELETE /assets/:id/tags/:tagId`                       | `{ count, tag }`，`tag` 为解除关联后的标签摘要                          |

代码：`apps/server/src/modules/collections/albums.service.ts` 的 `addAssets` / `removeAssets`；`tags.service.ts` 的 `addToAsset` / `removeFromAsset`。

这是小范围的返回字段扩展，不需要为性能改造增加数据库迁移。**前后端须配套发布，先发布兼容旧前端的服务端，再发布依赖这些新字段的前端。** 其他功能已有的数据库迁移不在此结论内。

### 2.4 请求调度与缓存

- 去掉全局 `revision` 广播；`perform` 必须显式提供成功后的更新回调。
- `useRemoteData`、`useAssetFeed` 在 KeepAlive 页面失活时停止发起查询，重新进入时只加载已标记失效的数据；本地状态仍可接收操作结果。
- 有必要的失效按 `assets`、`search`、`albums`、`tags`、`admin`、`places`、`ai`、`overview` 区分；即时失效合并 150ms，批量操作结束后再统一发送。
- overview 合并并发请求，普通读取有 5 秒新鲜度窗口；已知变化直接更新统计。分享保存等延迟失效会取消该新鲜度，进入工作区后再获取。
- `useVisiblePolling.ts` 在浏览器标签页隐藏、组件失活或关闭自动刷新时暂停调度；上一次轮询完成后才安排下一次，避免重叠。
- 工作区默认 30 秒读取统计；任务页接管自身轮询，待处理时 10 秒、空闲时 30 秒，避免布局同时重复轮询。任务列表加载超过 40 项时不自动重置列表。
- AI 摘要待处理时 5 秒、空闲时 60 秒读取；单张识别只在待处理或处理中轮询。
- 缩略图增加仅内存的 LRU Blob 缓存：最多 80 项、24 MiB、命中有效期 60 秒。缓存键区分账户、会话、资产、回收站状态和媒体版本；退出清空。组件仍负责释放自己的 Object URL。
- **公开分享缩略图不复用该缓存**，避免缓存命中绕过后续的短链撤销检查；不把私有图片写入持久化共享缓存。
- 用于本地更新的已知资产缓存上限为 2000 项；当前选中资产可由页面已有数据补入，避免仅因缓存淘汰就重新查询。

### 2.5 有意保留的请求与一致性边界

1. **首次进入、筛选变化、分页、显式刷新**：客户端没有对应数据，仍需查询。删除用户列表最后一条后进入上一页，也需要加载那一页。
2. **上传完成**：现有上传返回值不是完整图库摘要，秒传还可能命中已有资产，因此合并刷新资产和 overview，而不是伪造缩略图、标签或统计。地点与 AI 仅延迟失效。
3. **异步处理**：入队成功不代表转码或识别完成。只本地设为待处理，实际结果由可见页面的轮询获取。批量 AI 入队仅返回 `queued`，不足以推导所有状态分布，保留一次 AI 范围的查询。
4. **服务端筛选与未知关系**：标签改名/合并可能改变搜索结果，未分类视图可能缺少完整相册关系；只对这些结果失效，不能用当前 40 项推导整个数据库。恢复、回收后未知的自动封面或关联统计也延迟更新。
5. **本地缺少原状态**：不凭空累加全库统计。必要时只查询 overview；首个列表响应与相对计数变更同时发生时，允许范围内重新校准一次，避免重复加减。
6. **旧响应竞争**：已加载详情的局部更新会阻止旧请求回写；加载中的资产列表会重放期间的绝对字段变更。切换查询条件时清理旧查询的待应用变更。
7. **其他设备的变化**：本地更新只保证当前会话内操作的同步，不冒充跨客户端实时推送。显式刷新、已有统计轮询或未来的事件推送用于校准。
8. **认证和安全**：CSRF、JWT 撤销、用户状态、资源所有权、分享有效性、事务与存储引用检查均保留；不能以减少请求为由删掉这些检查。

## 3. 性能问题清单（原始发现）

以下保留初次审查时的问题依据、触发条件、建议及验收方向，便于追踪优化原因。部分代码位置已随改造变化，实施历史见第 7 节，**最新复审结论以第 8 节为准**，不要把原始发现直接当作当前代码行为。

### 3.1 前端渲染、缓存与资源

#### P1-01：长列表没有虚拟化，缓存页面仍持有大量 DOM 和数据

- **依据**：`apps/web/src/components/media/AssetGrid.vue:37`、`:124` 使用普通 `v-for`；`useAssetFeed.ts` 分页追加数组；`WorkspaceLayout.vue` 的 `<keep-alive>` 没有 `max`。
- **影响**：连续加载、切换多个媒体页面后，DOM、响应式数据和已解码图片增多。暂停请求及 24 MiB Blob 缓存不等于限制了解码内存或列表大小；局部变更仍需扫描缓存列表。
- **建议**：网格和列表使用虚拟窗口，保存滚动锚点；给页面/数据缓存设置上限；必要时按资产 ID 建索引，减少更新时遍历未受影响的列表。
- **验收**：对不同数量级的媒体持续滚动和切页，比较 DOM 数、堆内存、INP、回到页面的滚动位置和选中状态，而不是只看接口数量。

#### P1-02：同一资源的并发请求尚未统一合并

- **依据**：多个相册/标签选择器及页面各自调用 `useRemoteData(mediaApi.albums/tags)`；多个 `AssetImage.vue` 同时展示相同资产时，内存缓存尚未填充，仍会各自请求。
- **影响**：初次打开弹窗、列表与封面同时出现、多个面板并排时，仍有相同 URL 的并发读取。本次只合并 overview，并未实现通用查询缓存。
- **建议**：增加按账户、资源、筛选条件分键的短期查询缓存和 in-flight Promise 复用，引用计数管理取消；公开分享必须单独设计撤销语义。
- **验收**：同一键的并发消费者共享一次读取；取消一个消费者不影响其他消费者；切换账户、权限或资源版本后不复用旧结果。

#### P2-01：相册、标签列表无分页，详情页有重复读取

- **依据**：`AlbumsService.list`、`TagsService.list` 查询全部集合并包含封面/计数；`apps/web/src/views/tags/detail.vue` 为找一个标签请求全部标签；`mediaApi.album` 请求 `?limit=1`，随后 `AssetBrowser` 独立请求相册资产页。
- **影响**：集合很多时，弹窗和详情也传输整份列表；相册详情加载的 1 个资产与成员列表查询重叠。
- **建议**：为集合列表增加分页/搜索和轻量选择器接口；补单标签摘要接口；相册摘要与成员分页分开，或由页面复用同一分页响应。
- **验收**：集合数量增大时单次返回大小有上限；进入详情不会为了标题读取全部集合，也不重复查询成员。

#### P2-02：批量标签修改仍是 N 次写请求

- **依据**：`TagAssignmentDialog.vue`、`AssetBrowser.vue` 的 `removeFromTag`、`views/tags/detail.vue` 的 `addAssets` 都逐资产调用接口。
- **影响**：本次已去掉每次写入后的重复读取，但选中 N 张图仍有 N 次鉴权、HTTP 往返和事务；串行处理放大网络延迟。
- **建议**：增加有数量上限的批量标签接口，返回每项结果及受影响标签摘要；规定整批回滚或部分成功语义。暂用并发也应有上限，不能直接无限 `Promise.all`。
- **验收**：批量操作请求数随批次而非图片数增长；部分失败可恢复且成功项不会再次扣增计数。

#### P2-03：不同展示尺寸共用偏大的缩略图规格

- **依据**：`apps/server/src/modules/jobs/media-processing.constants.ts:7` 的缩略图最大边 1024、质量 90；前端小列表、封面、网格统一请求 `size=sm`。
- **影响**：几十像素的预览也可能下载和解码远大于展示需求的图片。
- **建议**：按展示尺寸和 DPR 提供多档缩略图，并纳入版本及缓存键；保留高清预览，不以重新模糊缩略图为代价追求小文件。
- **验收**：比较各档传输字节、解码时间，并人工确认高 DPR 屏幕的清晰度。

#### P2-04：部分原图/视频预览等待完整 Blob

- **依据**：`OriginalMediaViewer.vue` 的非 HLS 分支与 `SharedImageViewer.vue` 通过请求取得完整 Blob 后展示。
- **影响**：大图片等待下载完成才呈现；非 HLS 视频分支还可能占用较多内存。已有 HLS 与 Range 能力，不能把所有视频都视为整文件下载。
- **建议**：优先展示已有预览，再按需加载原图；对适合的媒体复用安全的短时流式票据/Range，限制预加载和原图并发，保留 Blob URL 释放。
- **验收**：比较首帧/首图时间和峰值内存；过期票据、所有权和分享撤销行为不退化。

#### P2-05：字体及样式影响首屏资源体积

- **依据**：`apps/web/src/assets/fonts.css:1` 引用约 2.2 MiB 的 TTF，没有 `font-display`；`main.ts:3` 全量引入 Element Plus CSS，`vite.config.ts` 的 resolver 设置 `importStyle: false`。
- **影响**：字体阻塞文字显示的风险及额外下载；首次加载包含并非当前页面所需的组件样式。Element Plus JS 已按需解析，不能误报为整个 JS 库全量导入。
- **建议**：确认字体许可后转 WOFF2、子集化并配置合适的 `font-display`；评估按需样式或关键样式，避免遗漏弹层样式。语言包是否拆分应先看实际体积。
- **验收**：记录冷缓存首屏传输、FCP/LCP、字体切换产生的 CLS，以及中英文/弹窗样式完整性。

#### P2-06：请求层统一 `no-store`，稳定资源无法使用 HTTP 缓存

- **依据**：`apps/web/src/api/request.ts:191` 统一设置 `cache: "no-store"`。
- **影响**：即使服务器提供校验信息，稳定元数据、版本化私有媒体也不会直接受益于浏览器缓存；本次内存 Blob 缓存仅覆盖部分缩略图复用。
- **建议**：按资源分级设计私有缓存、条件请求与 TTL，先从不敏感的版本化静态资源开始；不要给所有 JSON、鉴权接口或分享内容改成公共缓存。
- **验收**：命中策略确实减少传输；退出、撤销、换号和权限变化仍生效，私有内容不会被公共代理缓存。

### 3.2 服务端查询、鉴权与分享

#### P1-03：图片请求重复执行串行鉴权读取

- **依据**：`apps/server/src/modules/iam/auth/strategies/jwt.strategy.ts` 的 `validate` 依次读取 token 黑名单、可选会话撤销键、`getSessionVersion`、`getAuthUser`；`user.service.ts` 的 `getSessionVersion` 每次查数据库。
- **影响**：一页多张缩略图放大 Redis 往返和用户状态查询；命中认证资料缓存仍不等于没有数据库访问。
- **建议**：先合并/并行独立 Redis 读取；再评估具备可靠失效传播的会话版本缓存或复用现有媒体票据，禁止以长 TTL 缓存替代即时撤销检查。
- **验收**：按一屏图片统计 Redis/DB 次数和鉴权耗时，同时保持停用账户、修改授权、退出所有设备的失效语义。头像已从认证缓存分离，不是此处遗留问题。

#### P1-04：overview 与 AI 状态每次重新聚合

- **依据**：`asset-workspace.service.ts:30` 的 overview 执行资产 `groupBy`、收藏计数、相册计数、标签计数；`ai-index.service.ts` 的 `status` 重新 count/groupBy。
- **影响**：前端轮询已减少，但大图库和多用户并发时仍重复扫描/聚合相同状态。
- **建议**：按用户维护短期聚合缓存或事务内增量计数，后台处理和分享保存同样发布失效；保留周期校准，防止统计永久漂移。
- **验收**：观察统计接口的查询数、扫描行数、p95 与缓存命中；对上传、回收、恢复、分享、任务状态迁移核对汇总一致性。

#### P1-05：关键词包含匹配缺少对应文本索引

- **依据**：`assets/asset-filters.ts` 对每个关键词组合文件名、识别 `searchText`、标签名的 `contains` / `insensitive` 条件；当前 Prisma schema 和迁移未发现 trigram/全文索引。
- **影响**：多个 `%关键词%` 条件及关联过滤在媒体数量增加时可能退化为大量扫描，普通 B-tree 不能直接解决中间包含匹配。
- **建议**：先获取真实 SQL 与执行计划，再选择 `pg_trgm`、全文检索或规范化索引字段；明确中文、转义字符、多关键词 AND 和用户隔离语义。
- **验收**：以不同图库规模和关键词数量比较扫描行数、p95、索引体积及写入成本，不凭索引名称判断收益。

#### P1-06：地点分组在请求中读取并聚合 EXIF JSON

- **依据**：`asset-workspace.service.ts:73` 的 `places` 从 JSON 中取坐标、转数值、分桶、分组并计算窗口计数，`LIMIT 500` 在聚合之后。
- **影响**：返回 500 组并不意味着只处理 500 张图片；图库增大后重复解析 JSON 和分组的成本增长。
- **建议**：入库时提取规范化坐标/地理网格列，设置适配索引，按用户缓存或增量维护地点计数；保留无效坐标过滤。
- **验收**：比较扫描规模和执行计划；极值坐标、空值、删除/恢复后的地点统计保持一致。

#### P1-07：存储引用清理逐对象查询，索引覆盖不足

- **依据**：`asset-workspace.service.ts` 的 `purge` 对每个不同存储键串行执行 FileNode 四列 OR 的引用计数和 UploadSession 计数；`media-processor.service.ts` 的 `discardReplaced` 也逐对象计数。
- **索引现状**：FileNode 已有 `[storageProvider, storageKey]` 复合索引，不能说原文件键完全无索引；但查询没有限定该前导字段，且缺少 `thumbnailKey`、`previewKey`、`hlsKey` 的对应索引，四列 OR 不保证有效利用现有索引。
- **影响**：批量清理需要 O(存储键数量) 次数据库往返，且可能重复大范围扫描。
- **建议**：根据执行计划补适配索引，批量检查引用；长期考虑独立存储对象/引用表。与分享保存共用对象时，必须保留并发锁、事务和引用安全。
- **验收**：比较每批 SQL 数、扫描行数和耗时；仍被其他用户、资产或上传引用的对象绝不能删除。

#### P2-07：媒体热路径读取完整记录，并有重复文件系统检查

- **依据**：`AssetsService.findOwned`、`MediaStreamService.findOwned` 未为流式读取缩小 select；`ThumbnailsService.resolve` 的存在性检查及 `streamStoredMedia`、`local-fs-storage.provider.ts` 的 stat/read/open 路径包含多步检查。
- **影响**：单张图片或 HLS 分段也可能读取不需要的 EXIF 等列；本地/挂载存储延迟会放大多次元数据往返。
- **建议**：拆分媒体传输所需的轻量投影，传递已验证的记录或文件句柄，合并可安全复用的检查，不移除路径、符号链接或文件身份校验。
- **验收**：统计单个缩略图/分段的 SQL、返回列体积和文件系统调用次数，同时保留路径逃逸与文件替换防护。

#### P2-08：分享页按图片重复解析分享与归属信息

- **依据**：`shares.service.ts:207` 的 `media` 先解析分享、分享者权限及成员关系，再进入资产服务；`detail` 每次分页还查询全量匹配计数。
- **影响**：一个相册页面展示多张缩略图时，重复读取同一分享及分享者信息；翻页反复计算相同总数。
- **建议**：合并校验和轻量资产查询，分页使用一致的快照/版本信息；若引入缓存或短时票据，必须明确撤销、过期、移出相册和分享者停用的失效机制。
- **验收**：比较一页 N 张图的 SQL 总量；不能用「缓存命中」跳过有效性与成员资格校验。

#### P2-09：重复保存分享前仍加载全部来源资产

- **依据**：`shares.service.ts:219` 的 `save` 在读取幂等保存记录前，已 `findMany` 加载最多 501 条完整来源记录。
- **影响**：已保存过的用户再次点击保存，虽然不复制文件，仍可能读取整个相册的 EXIF 等数据并进入写事务。
- **建议**：保留分享/用户有效性校验后尽早检查既有保存记录；首次保存才查询复制所需字段。调整时保留串行化事务、唯一约束和来源行锁。
- **验收**：重复保存的读取规模不随相册大小增长；并发保存仍只有一份结果，撤销/失效规则不改变。

#### P2-10：管理用户列表携带内联头像

- **依据**：`apps/server/src/modules/iam/user/user-management.service.ts:24` 的分页 `userSelect` 包含 `avatar`，头像为最长 65536 字符的 data URL。
- **影响**：即便表格仅需少数字段，每页也可能携带多份较大头像，增加数据库传输、JSON 编码及浏览器解析成本。
- **建议**：列表使用轻量投影，按需取头像或独立受控头像地址；资料编辑继续返回完整资料，不重新塞回认证缓存。
- **验收**：比较每页 JSON 原始/压缩体积，并确认管理列表、头像和编辑功能不缺字段。

#### P2-11：大型标签合并将全部关联加载进应用事务

- **依据**：`apps/server/src/modules/collections/tags.service.ts` 的合并分支读取源标签全部资产 ID，再在事务中 `createMany` 并去重。
- **影响**：热门标签关联很多资产时，Node 内存、事务时长、参数数量及串行化重试成本增加。
- **建议**：评估数据库 `INSERT ... SELECT ... ON CONFLICT` 等集合操作；或采用有明确一致性策略的分块任务，而不是随意拆散事务。
- **验收**：大标签合并的峰值内存、锁等待和重试率可控；回收站关联、去重及源标签删除语义不变。

#### P3-01：权限父链校验逐级查询

- **依据**：`apps/server/src/modules/iam/permission/permission.service.ts` 的父节点校验沿父链循环读取。
- **影响**：权限树很深时，单次保存的数据库往返数随深度增加；通常低频，优先级低于媒体热路径。
- **建议**：使用递归查询或一次加载所需邻接关系，保留循环检测和并发一致性。
- **验收**：长链校验的 SQL 次数有界，循环、跨分支及并发修改仍正确拒绝。

### 3.3 上传与后台任务

#### P2-12：媒体任务补投串行等待发布确认

- **依据**：`apps/server/src/modules/jobs/media-jobs.service.ts:233` 的 `reconcile` 按批读取任务，循环 `await publish`；默认定时补投有间隔和批量上限。
- **影响**：队列恢复时，大量积压任务受串行网络确认及扫描间隔限制，恢复吞吐与正常消费能力可能不匹配。
- **建议**：有界并发发布、背压和分批续扫，避免无限并发；按积压量调整调度，保持去重和重试安全。
- **验收**：记录故障恢复后的补投速率、积压清空时间、重复消息数和 broker 压力。

#### P2-13：待处理缩略图重试仍可能重复投递任务

- **依据**：`ThumbnailsService` 在缩略图未就绪时走 enqueue 路径；`MediaJobsService.enqueue` 会检查状态并发布，消费者通过领取/租约避免重复处理。
- **影响**：多视图或多个客户端同时请求同一待处理资产时，虽然消费者防止并发重复处理，数据库检查和重复消息成本仍存在。
- **建议**：增加短时去重的投递状态或可靠 outbox，区分已排队、处理中和需要补投；防止去重标记让丢失任务永久得不到恢复。
- **验收**：同一资产并发预览不会线性增加消息；发布失败、租约过期和进程重启仍能恢复。

#### P2-14：AI worker 空闲时仍固定轮询

- **依据**：`apps/server/src/modules/ai/ai-worker.service.ts` 固定周期读取可运行任务；多实例各自查询，领取机制解决并发正确性但没有消除空轮询。
- **影响**：无任务期间仍有数据库负载，实例数越多越明显。
- **建议**：空闲退避并加抖动，或接入可靠事件唤醒/队列；保留定期兜底扫描和租约恢复。
- **验收**：比较空闲 SQL 次数、首次任务等待时间及多实例争抢率。

#### P2-15：分片上传状态查询反复 stat 所有已上传分片

- **依据**：`apps/server/src/modules/uploads/uploads.service.ts:481` 的 `sessionView` 读取所有分片，并以每组 16 个的并发度逐个 `storage.stat`。
- **影响**：分片越多，状态查询越重；合并等待期间的轮询反复做相同 I/O。现有 16 并发是正确的上限保护，但总工作量仍是线性的。
- **建议**：轻量进度接口与断点恢复完整校验分离，上传成功持久化可靠计数；仅恢复/合并前做必要的全量校验，不能把未落盘分片当作已完成。
- **验收**：日常进度查询 I/O 不随全部已上传分片增长；断点续传仍能发现丢失或损坏的分片。

#### P2-16：临时上传清理的批量与串行处理限制积压回收

- **依据**：`uploads.service.ts` 的清理流程每轮选择有限数量终态会话，读取其分片并逐会话清理。
- **影响**：高上传量或长期停机后，残留分片可能需要多轮才能回收；不能只用每轮耗时短来判断系统没有清理压力。
- **建议**：监控待清理量和最老残留年龄，以有界并发/时间预算连续处理积压，避免阻塞上传请求。
- **验收**：长期输入速率下清理吞吐跟得上产生速率；活动会话和被引用对象不受影响。

#### P2-17：清空回收站先在浏览器枚举全部资产

- **依据**：`apps/web/src/views/trash/index.vue` 的 `emptyTrash` 循环拉取完整资产页，收集全部 ID 后再每 100 项调用永久删除。
- **影响**：很大的回收站需要多次列表请求、传输不用于确认的资产字段并保存 ID；超过本地缓存上限时还无法完整增量计算统计。
- **建议**：提供服务端按确认快照/截止时间执行的清理任务，返回进度与汇总；至少先提供轻量 ID/汇总查询。保留「确认后新进入回收站的资产不被误删」规则。
- **验收**：浏览器内存和请求数不随回收站所有记录线性增长，取消、部分失败和进度展示有明确语义。

## 4. 需要运行环境确认，不能直接认定为故障

- **反向代理与 CDN**：仓库配置不足以证明生产环境是否启用 Brotli/gzip、HTTP/2/3、静态资源长期缓存或合理超时。上线环境应检查真实响应头和瀑布图，不能默认添加公共缓存到鉴权媒体。
- **数据库容量与连接池**：慢 SQL、连接等待、统计信息过期、硬盘吞吐和实际数据分布必须结合部署监控确认；不要仅凭静态代码调整连接数或为每个字段建索引。
- **存储全目录统计**：`local-fs-storage.provider.ts` 存在递归 `usage()` 实现，但本次未发现业务调用者，属于未来使用时的风险，不应计入当前请求的已确认热点。
- **语言包和打包体积**：语言字典共同加载、组件依赖大小可继续检查，但未做 bundle 分析，不能声称某个 chunk 超标或给出压缩后节省比例。

## 5. 保留的有效性能与安全设计

- 图库使用游标分页，筛选条件变化会重置游标，不用深 OFFSET 翻页替代。
- 上传哈希已有 Worker，上传/文件清理有并发上限和重试；不是所有耗时任务都在浏览器主线程或请求线程执行。
- 媒体转码走后台任务；当前业务已取消媒体上传的像素门槛，但字节数、格式、帧数及超时校验仍保留。不能为追求速度绕过输入安全检查，也不能以性能优化为由重新限制上传像素；大尺寸媒体的资源隔离问题见 R-B04。
- 大文件已有流式下载、Range 与 HLS；优化应复用这些能力，不退回整文件缓冲。
- Object URL 会释放；认证资料不缓存头像；分享保存复用不可变存储对象但有独立记录、幂等约束和引用保护。
- 登录背景已整合为单个本地 SVG，不再请求多张第三方图片，本次不重复改造。

### 8.3 前端：操作次数、请求次数与回流重绘

#### R-F01（P1）：上传完成后二次归档，批量刷新没有按上传批次收敛

- **依据**：`apps/web/src/stores/uploads.ts:146` 的 `finish` 对每个带相册的文件再次调用 `addToAlbum`；而 `apps/server/src/modules/uploads/uploads.service.ts:368` 已在完成事务中关联相册，秒传路径也已有相册关联。`apps/server/src/modules/collections/albums.service.ts:185` 即使关联已存在，仍执行授权、归属检查、去重写入及摘要读取。
- **请求放大**：正常上传到相册，每个文件额外产生 1 次归档 POST，而不是用户又做了一次归档操作。`apps/web/src/stores/uploads.ts:141` 随每个新完成文件失效 `assets/overview`；`apps/web/src/stores/workspace.ts:118` 只合并 150ms 内的失效，并强制重读 overview。文件完成间隔超过该窗口时，一批上传会多次重取活动列表和统计；已有 5 秒新鲜度不能挡住强制读取。
- **建议**：上传完成/秒传响应返回服务端实际完成的相册关联摘要及足够的资产字段，前端直接应用；仅兼容未绑定目标相册的旧会话时再补归档。对仍需校准的数据采用上传批次或带最大等待时间的节流合并，慢请求期间只记一次待刷新，不反复中止重发。保留秒传幂等、部分成功和撤权处理，不能简单删除请求后猜计数。
- **后续核验**：一次带相册上传不再出现第二次归档 POST；批量上传的列表/统计刷新按明确的合并窗口或批次发生，而不是按文件线性增长。前端 abort 不等于后端已开始的 SQL 自动取消。

#### R-F02（P2）：缩略图缓存键分裂，已有在途请求复用不能覆盖相同图片

- **依据**：`apps/web/src/components/media/AssetImage.vue:42` 把 `props.version` 纳入缓存及 `sharedRead` 键；`apps/web/src/components/media/AssetGrid.vue:58` 传入状态，例如 `READY`；`apps/web/src/components/media/AssetDetailDrawer.vue:174` 传入 `READY-0` 一类本地版本；`apps/web/src/views/albums/index.vue:212` 的封面不传版本。
- **触发与影响**：同一账户、同一张已就绪图片同时出现在列表、抽屉、封面时，三种键不能共享在途结果或 Blob。它们最终调用的却是同一个缩略图 URL，见 `apps/web/src/api/media.ts:88`；三个冷键可各触发一次 GET，占用重复缓存空间。返回 Blob 后各自创建 Object URL，缓存命中也不代表浏览器一定复用同一次解码。
- **建议**：统一使用资产真实派生版本构成的规范化键；手动刷新通过统一失效机制处理，不以组件私有后缀永久分裂缓存。继续隔离账户、会话、回收站状态和公开分享，不能为了复用绕过权限撤销。
- **后续核验**：同一版本在多个私有视图并发出现时只发生一次实际读取；媒体重处理、手动刷新、切换账户后仍能正确失效。

#### R-F03（P1）：DOM 虚拟化了，但每次局部更新仍操作整份已加载数据

- **依据**：`apps/web/src/composables/useAssetFeed.ts:84` 对整个列表 `map/filter`，有变化就在 `apps/web/src/composables/useAssetFeed.ts:126` 全量排序；`apps/web/src/composables/workspaceUpdates.ts:8` 对每项执行批量 ID 的 `includes`。`apps/web/src/composables/useAssetFeed.ts:232` 的订阅在 KeepAlive 失活时仍处理本地变化，失活只暂停请求。`apps/web/src/components/media/VirtualAssetRows.vue:39` 在列表引用变化时重新计算全部资产的列位置和高度。
- **放大机制**：一条收藏/改名就可能扫描多个缓存页，虽然这些操作并不改变 `createdAt/id` 排序键。批量 ID 匹配可达到「已加载资产数 × 批量 ID 数」的比较规模，随后还有排序和虚拟布局计算。`apps/web/src/composables/useAssetFeed.ts:198` 持续累积分页数据，且每次加载后重新登记整份列表；全局 2000 项已知资产缓存和 6 页 KeepAlive 不限制单个 feed 的数据长度。
- **建议**：用 ID 索引和批次共享的 Set 定位变更；仅插入、删除或排序字段变化时调整顺序。几何布局缓存只由宽度、尺寸和成员顺序驱动，不因收藏/名称变化全部重算；失活页可合并变更后再应用。进一步设计分页数据窗口和滚动锚点，不丢失选中状态。
- **后续核验**：长列表中改一个名称时，比较 JS 调用耗时、列计算次数、堆内存和 INP。不能因为只有少量可见 DOM，就认定状态更新成本已经是常量；也不能把这些数组遍历次数直接称为回流次数。

#### R-F04（P2）：原图缩放每次交错读取尺寸、修改尺寸、再读取尺寸

- **依据**：`apps/web/src/components/media/OriginalMediaViewer.vue:263` 的 `zoomTo` 读取边界与 `clientWidth/clientHeight`，修改 `scale`，等待 `nextTick` 后又读取尺寸并写滚动位置；`apps/web/src/components/media/OriginalMediaViewer.vue:73` 把缩放结果绑定为 DOM 的 `width/height`。`apps/web/src/components/media/OriginalMediaViewer.vue:300` 对每个 wheel 事件调用它，`apps/web/src/components/media/OriginalMediaViewer.vue:328` 对每个 pointermove 写滚动位置。
- **触发与影响**：触控板连续缩放、大图拖动时，没有帧级合并；尺寸写入影响布局，DOM 更新后立即读取几何信息可能触发同步布局。`nextTick` 只保证 Vue 更新完成，不保证浏览器已经布局/绘制。滚动写入也会增加渲染调度，但不必然每次都发生完整重绘。
- **建议**：使用 `requestAnimationFrame` 合并一帧内输入；集中读取并复用视口几何信息，随后统一写入。评估固定画布配合 `transform` 缩放和平移，仅在需要更新滚动范围时提交布局尺寸；保留指针锚点、边界和可访问性，不把所有动画一概改为 transform 就宣称没有绘制成本。
- **后续核验**：在 Performance 中比较一次连续缩放的 Layout/Paint、强制布局栈、长任务和掉帧。本文不提供未经采样的「每次缩放发生几次回流」。

#### R-F05（P2）：集合列表和选择器仍全量获取、过滤、排序、挂载

- **依据**：`apps/web/src/components/media/AlbumPicker.vue:21` 读取完整目录，并在 `apps/web/src/components/media/AlbumPicker.vue:93` 生成全部选项；`apps/web/src/components/media/TagManager.vue:50` 对输入做本地过滤和排序。`apps/server/src/modules/collections/albums.service.ts:74`、`apps/server/src/modules/collections/tags.service.ts:39` 的列表查询没有分页上限，且带封面/最新资产与计数；共享相册还附带创建者和当前成员权限。
- **影响**：目录缓存仅减少重复读取，不限制首次传输体积、后端关联聚合和浏览器 DOM 数。相册、标签很多时，打开选择器也承担卡片列表所需的完整摘要成本；本地筛选随每次输入重扫。此项是旧 P2-01 的剩余部分，不是「相册详情重复读取资产页」——当前详情已调用独立摘要接口。

- **后续核验**：目录数量增加时单次响应和挂载选项数有上限；记录打开弹层和连续输入的脚本、布局耗时。不要仅依据 Prisma `include` 就把关联查询断言为 N+1，需查看实际 SQL。

#### R-F06（P2）：非视频状态仍有轮询，用户不操作也有持续请求

- **依据**：`apps/web/src/components/workspace/WorkspaceLayout.vue:69` 每 30 秒读 overview；`apps/web/src/components/media/ImageRecognitionPanel.vue:37` 在图片识别处理中每 5 秒读结果；`apps/web/src/components/media/AiIndexStatus.vue:32` 按待处理/空闲状态每 5/60 秒读 AI 概览；`apps/web/src/views/tasks/index.vue:68` 按 10/30 秒周期读取任务列表及统计。
- **边界与影响**：`apps/web/src/composables/useVisiblePolling.ts:19` 已处理标签页可见性、KeepAlive、自动刷新开关和轮询不重叠；任务页已经替代布局层的统计轮询，且只有已加载不超过 40 项、没有重试及选中详情时才轮询列表，不能重复或无条件计数。但多个可见窗口仍各自查询，相同未变化结果仍需网络、解析和聚合。忽略请求耗时的调度量分别约为每分钟 2 次 overview、12 次待处理识别、12 次待处理 AI 概览，属于配置推导，不是实测值。

- **后续核验**：无状态变化时请求显著减少；识别完成及时呈现，断线后能校准，且后台视频总结通知不被误停。

#### R-F07（P2）：图片原图仍等待完整 Blob，大尺寸图片的解码成本没有因此受限

- **依据**：`apps/web/src/components/media/OriginalMediaViewer.vue:128` 的图片路径、`apps/web/src/components/media/SharedImageViewer.vue:28` 均取得完整 Blob 后再设置 Object URL。

- **后续核验**：对高压缩、大尺寸图片记录首图时间、峰值内存、切换图片后的释放情况及原图清晰度。

#### R-F08（P2）：一次清空回收站操作仍需要全量读分页，再逐批删除

- **依据**：`apps/web/src/views/trash/index.vue:24` 在确认前按 100 项循环读取资产页并保存 ID；`apps/web/src/views/trash/index.vue:52` 确认后再按 100 项删除。

- **后续核验**：浏览器持有数据及控制请求不随整个回收站线性增长；明确取消、部分失败和重入的处理规则。

### 8.4 后端：I/O 交互、请求压力与后台处理

#### R-B01（P1）：文件已提交成功，上传响应仍等待逐分片清理

- **依据**：`apps/server/src/modules/uploads/uploads.service.ts:384` 在返回完成结果前 `await cleanupParts`；`apps/server/src/modules/uploads/upload-parts.service.ts:145` 先查询全部分片，再串行执行每片的存储删除和 `uploadPart.deleteMany`。
- **次数与影响**：有多少分片，就有多少次存储删除和数据库删除调用，另加一次分片查询。5 MiB 分片下，一个 512 MiB 视频可有 103 片，即该清理阶段可包含 103 次存储删除、103 次删除调用。此时仍占着 `apps/server/src/modules/uploads/uploads.service.ts:258` 的上传校验并发名额；存储或数据库延迟直接拉长完成响应，并推迟后续入队。这里不是旧版「合并进度轮询 stat 全部分片」问题。
- **建议**：完成事务之后通过持久化清理标记/任务回收分片，完成响应不等待清理全部对象；对已确认删除的分片有界并发清理并批量删除对应记录。不能只启动一个不受跟踪的异步 Promise，也不能先删数据库记录导致失败对象无法追踪。保留定期兜底、活动会话保护及幂等重试。
- **后续核验**：上传完成响应时长不再随清理分片数线性增加；同时观察清理积压、最老残留年龄、存储空间和重试，不以「响应快」掩盖垃圾增长。

#### R-B02（P1）：热路径仍逐请求读会话，共享上传还有重复作用域读取

- **依据**：`apps/server/src/modules/iam/auth/strategies/jwt.strategy.ts:37` 先 Redis MGET，再读会话版本、认证资料；`apps/server/src/modules/iam/user/user.service.ts:301` 的版本查询每次访问数据库，`apps/server/src/modules/iam/user/user.service.ts:103` 再读认证缓存。视频每次资源请求也执行 `apps/server/src/modules/assets/media-stream.service.ts:94` 的鉴权和资产范围查询。
- **次数与放大**：在认证资料缓存正常命中的常见路径，JWT 校验仍至少包含 1 次 MGET、1 次用户版本读取、1 次认证缓存 GET，之后才是业务查询。缺少全局上传权限的受邀成员还经过 `apps/server/src/modules/iam/auth/guards/permission.guard.ts:88` 的相册权限读取；`apps/server/src/modules/uploads/uploads.service.ts:220` 读取会话后，又通过 `apps/server/src/modules/uploads/uploads.service.ts:463` 查询相册权限。该开销随缩略图、HLS 分段和上传分片请求数重复。
- **建议**：先并行独立鉴权读取，并在单次请求范围复用可信的轻量授权上下文，减少相同相册/用户的重复加载；共享权限查询只选择必要字段。跨请求版本缓存或媒体会话缓存必须具有可靠失效机制。**事务内提交前的授权复核、资产范围、撤销和账户停用检查不能因去重而删除**；不得直接相信前端缓存的成员权限。
- **后续核验**：按「一屏缩略图」「一次 HLS 播放」「一个分片」统计 Redis/SQL 次数及鉴权耗时，同时验证撤权、成员移除、账号停用仍按既有语义生效。

#### R-B03（P1）：统计查询减少了调用数，但仍反复扫描和聚合相同数据

- **依据**：`apps/server/src/modules/assets/asset-workspace.service.ts:32` 每次 overview 执行资产分组、相册计数、标签计数三个 Prisma 查询；`apps/server/src/modules/ai/ai-index.service.ts:78` 每次 AI 概览执行图片 count 和识别状态 groupBy。
- **影响**：前端缓存/轮询退避不能让不同用户窗口或服务实例共享聚合结果。图库大、可见客户端多、上传失效频繁时，业务查询规模约随「有效请求数 × 各用户参与聚合的数据量」放大；共享相册的相册数还涉及成员及创建者有效性条件。旧 P1-04 只部分完成，不能再声称 overview 仍是四次查询。
- **建议**：为统计建立按用户隔离的短期服务端缓存与同键在途合并，再评估事务内增量统计或专门汇总表。上传、回收、恢复、任务迁移、分享保存、共享成员变化都需纳入失效；保留校准与权限变化处理。
- **后续核验**：比较聚合调用次数、扫描行数、缓存命中、数据库连接等待及 p95；无状态变化时多个同用户请求不应重复执行同一聚合。

#### R-B04（P1）：取消像素门槛后，需要隔离解码资源，而不是重新拒绝大图片

- **依据**：`apps/server/src/modules/uploads/uploads.service.ts:316` 在上传完成请求内读入图片并执行解码检查；`apps/server/src/common/image-inspection.ts:133` 配置 `limitInputPixels: false`，随后生成 64px 原始像素结果验证解码。`apps/server/src/modules/jobs/media-processor.service.ts:160` 的后台图片处理会再次读取、检查原图。
- **风险边界**：当前仍有 10 MiB 文件上限、帧数检查、10 秒解码超时和上传并发上限，不是毫无保护；但压缩字节上限和小尺寸输出不等于输入解码内存上限，具体成本依赖格式及解码器。Sharp 主要使用原生线程，不应描述成所有计算都同步阻塞 JS 主线程；它仍占用同一 API 进程的内存和 CPU。视频/AI worker 的并发也是各实例本地的，例如 `apps/server/src/modules/video-summaries/video-summary-worker.service.ts:76`，增加 API 实例可能同时增加后台处理及下游 ASR 压力。
- **建议**：保持任意像素原文件可上传的业务要求，将格式/安全验证与高成本派生处理合理分层，并把解码/转码放进独立、可终止且有内存、CPU、临时磁盘预算的 worker/容器。对高成本任务采用加权并发与下游 ASR 总并发控制；超预算时保留原文件并明确派生处理状态。不能跳过 SVG/格式安全校验后直接提供未经保护的内容，也不能仅增大超时来解决资源竞争。
- **后续核验**：记录不同格式和尺寸下的峰值 RSS、原生线程/CPU、临时空间、API 尾延迟及 ASR 排队时间；不能只凭压缩文件大小推导能同时处理多少张。

#### R-B05（P2）：视频全链路有多份完整临时副本，流式传输不等于少 I/O

- **依据**：`apps/server/src/modules/uploads/upload-validation.ts:73` 合并内容写入临时原视频，`apps/server/src/modules/uploads/uploads.service.ts:305` 检查后又读临时文件写入原文件存储；`apps/server/src/modules/jobs/media-processor.service.ts:478` 为转码复制原文件到临时目录；`apps/server/src/modules/video-summaries/video-transcription.service.ts:185` 为 ASR 再独立复制一次。
- **影响**：分片落盘后，仍有读分片/写合并临时文件、读临时文件/写原文件，以及转码、ASR 各自的完整读取和写入。即使没有整段 Buffer 常驻内存，大视频和多任务也会竞争磁盘带宽与临时空间；重试还可能再次复制。当前 ASR 会恢复已完成分段，不应误报为每次必然重转全部音频。
- **建议**：在存储抽象中提供受控的不可变对象本地读取能力，评估同文件系统原子接纳、受保护的只读句柄或安全临时链接，避免每个处理阶段复制全部数据；不满足条件时保留流式复制回退。继续保留哈希、完整性、符号链接/路径防护、引用保护和清理责任。
- **后续核验**：按单视频统计原文件相关读写字节及临时空间峰值，区分不同磁盘/挂载点，不能仅统计 Node Buffer 大小。

#### R-B06（P2）：ASR 每个检查点重写累计全文和全部分段

- **依据**：`apps/server/src/modules/video-summaries/video-transcription.service.ts:142` 每块将既有文本和分段复制到新结果，随后调用 checkpoint；`apps/server/src/modules/video-summaries/video-summaries.service.ts:278` 将累计结果写回，`apps/server/src/modules/video-summaries/video-summaries.service.ts:295` 进入总结阶段又写一次完整结果。
- **放大机制**：假设每块转写量接近，处理多个块时累计复制/持久化量是第 1 块到第 n 块前缀大小的总和，呈二次增长趋势，而不是只写最终文本一次。现有 5 分钟音频分块、4 小时时长及文本/分段数量上限使它有边界，但长视频仍会增加 JSON 序列化、数据库写入及 WAL 成本。SSE 不发送全文，并没有消除服务端检查点的全文写入。
- **建议**：用资产、源文件版本和分块编号唯一标识持久化分段增量，只更新小体积进度；全文在总结或用户读取时组装/物化。设计迁移和旧任务恢复方案，保留已完成分块的断点恢复，不为减少数据库写入而增加 ASR 重跑。
- **后续核验**：比较各检查点请求体积、数据库写入/WAL、任务 RSS 及失败恢复的 ASR 调用数。

#### R-B07（P2）：视频事件使用全局事务锁，不同用户的写入也会互相等待

- **依据**：`apps/server/src/modules/video-summaries/video-summary-state.ts:40` 每次记录事件都获取同一个 `pg_advisory_xact_lock(VIDEO_SUMMARY_EVENT_LOCK, 0)`，然后插入事件并执行 `pg_notify`；`apps/server/src/modules/uploads/uploads.service.ts:375` 的视频上传事务和 `apps/server/src/modules/video-summaries/video-summaries.service.ts:371` 的状态更新事务都会调用它。
- **影响与边界**：这些事件临界区按全局锁串行化，锁持有到事务结束；多用户集中上传、任务领取/完成时可能增加锁等待和连接占用。单次临界区目前较短，不能在未采样前认定已经成为瓶颈。该锁还保护提交顺序与 SSE 游标，不是可以随意删除的冗余代码。
- **建议**：先记录锁等待，再评估按用户事件流分区的锁/序号，或具备提交顺序保障的 outbox。任何替代都必须保证「较大事件 ID 已推送后，较小 ID 才提交」不会导致漏通知，不能单纯删锁或移到事务外通知。
- **后续核验**：多用户并发时测量事务锁等待；故意交错提交仍无事件遗漏，失败事务不发成功通知。

#### R-B08（P2）：SSE 虽不再轮询状态，连接扇出与历史补发仍需限量

- **依据**：`apps/web/src/composables/useVideoSummaryEvents.ts:44` 每个打开的工作区建立自己的连接；`apps/server/src/modules/video-summaries/video-summary-events.service.ts:48` 为每连接维护游标、订阅和鉴权状态，收到同用户通知后分别执行 `apps/server/src/modules/video-summaries/video-summary-events.service.ts:122` 的事件查询。`apps/server/src/prisma/schema.prisma:314` 的事件表只有主键、资产索引及随总结删除的级联关系，当前代码未提供按时间归档/清理。
- **放大机制**：同用户多个窗口会重复查询和编码相同事件；每连接还约 45 秒复核权限。历史补发虽每批最多 50 条，却会继续循环到追平，只有批内按资产合并，没有整轮时间/条数预算。旧游标、较多事件或通知连接恢复时可能集中回放；不是每连接占用一个 PostgreSQL LISTEN 连接。
- **建议**：同实例按用户共享实时事件读取/编码，连接仍保留各自权限与恢复游标；前端可通过同会话的 SharedWorker/BroadcastChannel 协调多窗口。制定事件保留期、每轮补发预算和过期游标的快照重置协议；评估事件冗余用户键及 `(ownerId, id)` 查询索引。限制每会话连接量并关注慢消费者背压，不以暂停隐藏窗口为由丢掉后台完成通知。
- **后续核验**：记录连接数、每事件数据库读取数、重连回放条数、待发送缓冲、事件表增长和通知延迟；撤权及游标恢复仍正确。

#### R-B09（P2）：缩略图成功 GET 对同一对象多次执行元数据检查

### 9.4 推送与刷新约定

```text
图片识别 / 媒体任务状态实际变化
  → 同一事务内更新记录 + PostgreSQL NOTIFY（租约续期不发送）
  → 复用每进程已有的 LISTEN 连接，按 ownerId 筛选
  → 现有 /video-summaries/events 发出 workspace-changed
  → 前端合并 ai / processing / overview / places / search 失效集合
  → 可见、启用自动刷新的页面按 5 秒窗口校准相关接口
```

- `connected` 数据新增 `workspaceUpdates: true` 用于能力协商；旧服务端没有该字段时仍保留原类周期读取，不把「视频 SSE 在线」误判为支持所有任务状态。
- `workspace-changed` 只承载资源名，不承载转写、识图全文或存储路径，也不推进视频事件游标。其通知通过事务提交发送，接收端每 1 秒合并一次；前端合并窗口与视频完成通知独立，视频原有即时结果合并不等待这 5 秒。
- 图片与媒体通知属于失效信号，不新增持久事件表。SSE 重连、PostgreSQL LISTEN 重连、页面重新可见和重新开启自动刷新时进行状态校准；低频校准覆盖通知丢失或其他窗口的数据变动，不声称提供可靠消息队列语义。
- 连接正常且页面可见时，布局统计、AI 概览和任务页以 5 分钟周期兜底；图片详情只在仍处于待处理/处理中时保留该兜底。推送不支持/断开时，图片识别与繁忙 AI 概览回退到 15 秒，空闲 AI 概览 60 秒，任务页 10/30 秒，非任务页统计 30 秒。
- 自动刷新开关与页面可见性同样约束新增推送触发的 GET。隐藏时只合并少量资源标记，不持续刷新页面；视频完成通知与后端执行不因该开关停止。
- 任务列表仍仅在已加载不超过 40 项、没有重试及选中详情时自动校准；失活页面不发请求。媒体任务通知不使其他长图库自动回到第一页，用户手动刷新和加载更多仍有效。
- overview 与通用详情读取在请求执行期间收到刷新需求时合并为一次后续读取，不再反复中止重发；资产分页仍回放读取期间收到的局部操作，避免旧响应覆盖已知本地修改。
- 这项优化用少量状态写事务中的 NOTIFY，替代客户端持续查询。实际请求数还受并发、窗口数、网络失败与任务密度影响，不能仅用定时间隔推算真实吞吐收益。

### 9.5 接口与部署

1. **先更新后端，再更新前端**。上传完成/秒传新增绑定摘要，资产与集合摘要新增缩略图版本；旧客户端会忽略新字段。新前端兼容旧上传响应和旧 SSE 能力，但 `GET /assets/trash/ids` 需要新后端。
2. `GET /assets/trash/ids?cursor=...` 需要 `asset:delete`，只返回当前用户回收站的 `{ items: [{ id }], nextCursor, hasMore }`，固定每页最多 1000 项。游标绑定用户及独立 scope，沿用 createdAt/id 顺序和格式校验，不接受客户端修改页大小来无限扩大读取。
3. `thumbnailRevision` 来自不可变派生存储键的 SHA-256，不返回存储键；没有派生键时用处理状态。原图票据继续逐次校验会话、撤销及可读取资源范围，GET/HEAD/Range 行为和安全响应头不放宽。
4. **事件锁变更需要统一切换后端进程**：停止旧版本任务写入者，统一重启所有 API/worker 实例后再恢复消费，避免旧单键锁与新按用户双键锁同时分配事件。不能仅滚动替换前端或长期混跑旧后台消费者。
5. 本轮优化无需额外迁移；已有视频总结、共享相册等功能依赖的迁移仍必须已应用。LISTEN/NOTIFY 仍需 PostgreSQL 直连或会话池化，反向代理继续关闭 SSE 缓冲并保留足够读取超时。
